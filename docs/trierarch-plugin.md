# The trierarch plugin: architecture

`@aeolus-fleet/trierarch-plugin`: a long-running Node process, hosted beside squadrons, serving every fleet of the server with one connection each and switched per fleet as squadrons is (decisions [0021](https://github.com/ThomasHendrickx/aeolus-fleet/blob/main/docs/decisions/0021-squadrons-installation.md), [0030](decisions/0030-trierarch-plugin.md)). It reaches each fleet only through the public API, as that fleet's trierarch plugin ship (`fleet:read`, `fleet:commission`, `crew:assign`, `crew:run`, `labels:define`, `labels:assign` and `scopes:declare`). It follows the fleet's changes, and every check-in returns the latest full state. Its configuration holds the trusted repositories, one list for every fleet it serves and every trierarch (aeolus-fleet#384). Its own small database holds per fleet only the connection (its ship and kept crew token) and the switch, set through installation procedures as squadrons' are, the fleet's enabled models ([0063](decisions/0063-model-governance.md)) and its usage history ([0030](decisions/0030-trierarch-plugin.md)); it may share squadrons' Postgres server, in its own schema. Everything else (requests, statuses, machines) lives in the fleet. It depends on `common` only.

What lives in core: the product and its language in aeolus-fleet's [blueprint](https://github.com/ThomasHendrickx/aeolus-fleet/blob/main/docs/blueprint.md), what the trierarch plugin and the trierarchs do in [docs/trierarch.md](https://github.com/ThomasHendrickx/aeolus-fleet-trierarch/blob/main/docs/trierarch.md), the crew request in decision [0029](https://github.com/ThomasHendrickx/aeolus-fleet/blob/main/docs/decisions/0029-crew-request.md), and the calls this package makes and the minimum core version it checks in [docs/compatibility.md](https://github.com/ThomasHendrickx/aeolus-fleet/blob/main/docs/compatibility.md).

| Layer | Pieces |
| --- | --- |
| Core (pure) | **Placement**: a pure function from (the unassigned requests, oldest first, the trierarchs' reports, the requests assigned to each) to the trierarch to claim for each, or the reason none fits; the only place that picks. It keeps the trierarchs that fit (repository, harness, model) and have room, then takes the most room as a percentage, then the oldest. In a fleet with enabled models, a request naming another model waits with `model disabled: <id>`, and one naming none fits only a trierarch whose default model for the harness is enabled (0063). **Assignment pass**: per fleet, read the unassigned requests and the trierarchs, place, then claim or write the reason; a lost claim is read again on the next pass. **Join**: refuse an actor without `trierarch:join` (argo always may), then commission a trierarch ship with `crew:run` and answer its starting prompt and the machine's setup line. **New setup line**: for a ship of type `trierarch`, release it when crewed, then get its new starting prompt, both as the operator with the forwarded console session and Origin so the operator's rights decide (0057), and answer the setup line built as at join; the old line stops working (aeolus-fleet#1239). **Machines**: the fleet's ships of type `trierarch`, each with its trierarch's report and details, whether it is silent, and their labels. **Network**: declare `trierarch=*` to `trierarch=*`, withdrawn when off or deleted. **Trusted repositories**: the one list, from the configuration, of the repositories a trierarch may clone on demand, each by name with an https or ssh git URL that holds no credential (aeolus-fleet#384); each pass sends it whole to every trierarch ship that is not retired, once per process, and again to a trierarch that asks for it. **Enabled models**: each fleet's set of exact model ids, read by every session, enabled and disabled with `fleet:manage`; the assignment pass and the check before a request read it each time (0063). **Keeping usage**: the plugin's ship takes what waits for it every second; a usage message (`application/vnd.aeolus.trierarch.usage+json`) from a ship of type trierarch, as the fleet reads the sender, parsing as common's schema, is kept as the sender's machine's and only then acked, so usage the store fails on is handed again, and the same hour handed again keeps the same rows; usage from any other ship, or one that does not parse, is acked and logged as not handled; argo's ping is answered with pong, and anything else acked. **Token usage**: the fleet's tokens in a range, hours up to 7 days and UTC days from their rollup past that, split by machine, harness, model, ship, login or token kind, the 7 largest series by tokens or estimated cost and other for the rest, filtered per breakdown, all in one query; machines and ships named from one read of the fleet's ships, retired ones included, read only when the split needs them; every session reads it. **Pruning usage**: once an hour, per connected fleet it serves, the retention `fleet.limits` answers its ship (decision 0066): the hours, UTC days and subscription readings wholly older than that many days go, a batch at a time; a fleet keeping its history for good, or switched off, is not pruned. **Usage values**: one breakdown's values in a range with their tokens, 20 a page by a cursor, largest first, for the Usage page's filter menus. **Subscription windows**: per machine and harness, 20 a page by a cursor, each window's readings in a range, the machine named from the fleet's ships. **Scopes**: declare the namespace `trierarch` with `trierarch:join` while its ship does not hold it; tell argo once while another ship does. **Connection**, **installation** and **operator** |

## Deployment

A long-running Node process beside squadrons, with a small Postgres database of its own holding each fleet's connection, switch, enabled models and usage history (it may share squadrons' Postgres server, in its own schema), on any VM or container host next to the server. It needs no public address: only the web app's server and the fleet's API talk to it or it to them.
