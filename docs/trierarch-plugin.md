# The trierarch plugin: architecture

`@aeolus-fleet/trierarch-plugin`: a long-running Node process, hosted beside squadrons, serving every fleet of the server with one connection each and switched per fleet as squadrons is (decisions [0021](https://github.com/ThomasHendrickx/aeolus-fleet/blob/main/docs/decisions/0021-squadrons-installation.md), [0030](decisions/0030-trierarch-plugin.md)). It reaches each fleet only through the public API, as that fleet's trierarch plugin ship (`fleet:read`, `fleet:commission`, `crew:assign`, `crew:run`, `labels:define`, `labels:assign` and `scopes:declare`). It follows the fleet's changes, and every check-in returns the latest full state. Its configuration holds the trusted repositories, one list for every fleet it serves and every trierarch (aeolus-fleet#384). Its own small database holds per fleet only the connection (its ship and kept crew token) and the switch, set through installation procedures as squadrons' are, the fleet's enabled models ([0063](decisions/0063-model-governance.md)), its crew-time MCP configuration with its deliveries, and its usage history ([0030](decisions/0030-trierarch-plugin.md)); it may share squadrons' Postgres server, in its own schema. Everything else (requests, statuses, machines) lives in the fleet. It depends on `common` only.

What lives in core: the product and its language in aeolus-fleet's [blueprint](https://github.com/ThomasHendrickx/aeolus-fleet/blob/main/docs/blueprint.md), what the trierarch plugin and the trierarchs do in [docs/trierarch.md](https://github.com/ThomasHendrickx/aeolus-fleet-trierarch/blob/main/docs/trierarch.md), the crew request in decision [0029](https://github.com/ThomasHendrickx/aeolus-fleet/blob/main/docs/decisions/0029-crew-request.md), and the calls this package makes and the minimum core version it checks in [docs/compatibility.md](https://github.com/ThomasHendrickx/aeolus-fleet/blob/main/docs/compatibility.md).

| Layer | Pieces |
| --- | --- |
| Core (pure) | **Placement**: a pure function from (the unassigned requests, oldest first, the trierarchs' reports, the requests assigned to each) to the trierarch to claim for each, or the reason none fits; the only place that picks. It keeps the trierarchs that fit (repository, harness, the MCP servers the request names, model) and have room, then takes the most room as a percentage, then the oldest. A trierarch fits a `repositories` workspace when its report's `workspaces.repositories` (configured or trusted) holds the main repository and every sub-repository; a request none fits waits with the first repository no trierarch offering its harness offers named in its reason, such as `no trierarch offering claude-code has repository skills`, or, when each is offered but none offers them all, `no trierarch offering claude-code has repositories aeolus-fleet, skills together`, and the settings check refuses it with the field `workspace`. A `folder` workspace fits a trierarch that offers the folder. A trierarch fits the servers when the harness the request uses reports every one in its `mcpServers`; a request none fits waits with the server named in its reason, such as `no trierarch offering claude-code offers MCP server company-graph`, and the settings check refuses it with the field `mcpServers` (aeolus-fleet-trierarch#120, M4). In a fleet with enabled models, a request naming another model, or one no trierarch offering its harness reports, waits with `model not available: <id>`, and one naming none fits only a trierarch whose default model for the harness is enabled (0063). **Assignment pass**: per fleet, read the unassigned requests and the trierarchs, place, then claim or write the reason; a lost claim is read again on the next pass. **Telling why a request waits**: after each assignment pass, per fleet, an unassigned request whose reason is `model not available: ...` or `given back by every trierarch that fits; last: ...` is told to the ship that last made it (`requestedBy`), as an `application/vnd.aeolus.trierarch.crew-request-reason+json` message from the plugin's ship with the ship, its settings version and the reason; a request with no requester, or a retired one, is told to argo, naming the ship, the requester and the reason. Once per ship, settings version and kind: the idempotency key is made from the three, so a restart and a rewritten reason tell nothing again, and a new settings version is told again. The read lists retired ships too, so a retired requester is seen as retired. A message to the requester the fleet refuses for good goes to argo under the same key, naming the refusal. No answer, a busy fleet, a server failure, the plugin's crew ended and the fleet's message limit are not final: nothing was stored, so the tell is made again next pass, never to argo in its place. Other reasons are not told; a tell the fleet does not answer is tried again by the next pass, one argo's tell is refused for good is tried no more, and the others go on either way. **Join**: refuse an actor without `trierarch:join` (argo always may), then commission a trierarch ship with `crew:run` and answer its starting prompt and the machine's setup line, which carries each harness and repository option the join was given as its flag (`--harnesses`, `--unattended` for the picked harnesses only, `--repositories`, `--repositories-in`, `--no-repositories`), every path or git URL shell-quoted, and never `--clone-into`; an option left out is asked on the machine, and the console builds no line (join design, decision 12). **New setup line**: for a ship of type `trierarch`, release it when crewed, then get its new starting prompt, both as the operator with the forwarded console session and Origin so the operator's rights decide (0057), and answer the setup line built as at join; the old line stops working (aeolus-fleet#1239). **Machines**: the fleet's ships of type `trierarch`, each with its trierarch's report and details, whether it is silent, and their labels. **Network**: declare `trierarch=*` to `trierarch=*`, withdrawn when off or deleted. **Trusted repositories**: the one list, from the configuration, of the repositories a trierarch may clone on demand, each by name with an https or ssh git URL that holds no credential (aeolus-fleet#384); each pass sends it whole to every trierarch ship that is not retired, once per process, and again to a trierarch that asks for it. **MCP configuration** (aeolus-fleet's [fleet crew MCP design](https://github.com/ThomasHendrickx/aeolus-fleet/blob/main/docs/design/fleet-crew-mcp/README.md)): each fleet's one current set of remote MCP servers (Streamable HTTP), each by name with its URL holding no credential, the tools a session may call and optionally a credential naming a secret and the HTTP header the trierarch's proxy sets to its value (decision M6), and the secrets with their values, each 1 to 8192 bytes of UTF-8 with no CR, LF or NUL. Version 0 with nothing before the first replacement. `mcp.get` answers it to a `fleet:manage` session, secret names only; `mcp.replace` replaces it whole from the version read, for a `fleet:manage` session whose Origin is the configured console origin, checked first: the complete server list, the secrets retained by name and the new or replacement values. The model refuses the whole replacement, with a reason naming no value, for a stale version (CONFLICT), a server or secret breaking a rule, a credential naming a secret not retained, a retained secret without a value, a value for a secret not retained, or a set that would not fit one 256 KB message once sealed. One transaction moves the version on only from the version expected, replaces the secrets and writes the value-free event (actor, version, changed names), so of competing writers one commits and a failure changes nothing. A value is never logged, answered or put in an event; a store failure answers an internal error with no detail. **MCP distribution**: each pass reads the fleet's set once, its servers and secrets from one snapshot, then each crewed trierarch ship that is not silent and states a sealing key, and sends what `nextMcpSend` says: the complete set at its version with every secret sealed to that key through the **Sealer** port (the NaCl anonymous sealed box), so the fleet stores only what it cannot read. A new attempt is kept with its idempotency key and message before the send; one the fleet did not take goes again the same under that key; one it took without a confirmation gets a new copy under a new key after 5 minutes; a new version, key or request gets a new attempt; confirmed for the current version and key, nothing. A trierarch seen not crewed is forgotten. No key, or one the Sealer refuses, sends nothing (the latter logged once per key). **MCP confirmations**: in the inbox round, before the ack, an applied message counts only from a crewed trierarch, naming this fleet and plugin ship, the current version and the key its last attempt was sealed to; a request message, which a trierarch sends when its lease starts, forgets its confirmation at once and marks it for a new copy; anything else of the contract is ignored and logged with a value-free reason. Placement treats a trierarch whose confirmation is not the current version and its reported key as offering no MCP server. 
**Enabled models**: each fleet's set of exact model ids, read by every session, enabled and disabled with `fleet:manage`; the assignment pass and the check before a request read it each time (0063). **Keeping usage**: the plugin's ship takes what waits for it every second; a usage message (`application/vnd.aeolus.trierarch.usage+json`) from a ship of type trierarch, as the fleet reads the sender, parsing as common's schema, is kept as the sender's machine's and only then acked, so usage the store fails on is handed again, and the same hour handed again keeps the same rows; usage from any other ship, or one that does not parse, is acked and logged as not handled; argo's ping is answered with pong, and anything else acked. **Enabled models ask**: a ship sends the plugin's ship `application/vnd.aeolus.trierarch.enabled-models-ask+json` (payload `{}`); in its inbox round the plugin replies (inReplyTo) with `application/vnd.aeolus.trierarch.enabled-models+json`, `{"models":[...]}` sorted, the fleet's set as it is then, an empty list meaning no rule (0063). No scope is checked. The reply is stored under a key made from the ask's message id before the ask is acked, so a database failure or a fleet that does not answer leaves the ask unacked and handed again, and a crash after the reply answers once. A fleet the plugin does not serve leaves the ask waiting. **Token usage**: the fleet's tokens in a range, hours up to 7 days and UTC days from their rollup past that, split by machine, harness, model, ship, login or token kind, the 7 largest series by tokens or estimated cost and other for the rest, filtered per breakdown, all in one query; machines and ships named from one read of the fleet's ships, retired ones included, read only when the split needs them; every session reads it. **Pruning usage**: once an hour, per connected fleet it serves, the retention `fleet.limits` answers its ship (decision 0066): the hours, UTC days and subscription readings wholly older than that many days go, a batch at a time; a fleet keeping its history for good, or switched off, is not pruned. **Usage values**: one breakdown's values in a range with their tokens, 20 a page by a cursor, largest first, for the Usage page's filter menus. **Subscription windows**: per machine and harness, 20 a page by a cursor, each window's readings in a range, the machine named from the fleet's ships. **Scopes**: declare the namespace `trierarch` with `trierarch:join` while its ship does not hold it; tell argo once while another ship does. **Connection**, **installation** and **operator** |

## Deployment

A long-running Node process beside squadrons, with a small Postgres database of its own holding each fleet's connection, switch, enabled models, MCP configuration and usage history (it may share squadrons' Postgres server, in its own schema), on any VM or container host next to the server. Its database is a credential store: each fleet's MCP secret values are readable to the service and its database administrators, its backups included, so protect its access and backups as the crew tokens it keeps. It needs no public address: only the web app's server and the fleet's API talk to it or it to them.
