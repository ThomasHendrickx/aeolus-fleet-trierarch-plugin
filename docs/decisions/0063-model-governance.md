# 0063 Model governance: the models a fleet may run

- Per fleet, the trierarch plugin holds the fleet's enabled models: a set of exact model ids, each one common's `modelSchema` takes, in its own table `enabled_models` (`fleet_id`, `model`). An empty set is no rule, and placement is as without it. A set with one id or more is the rule: only its models are placed. An id no trierarch reports may be in it. Deleting the fleet from the trierarch plugin forgets them with its connection and switch; switching the plugin off keeps them.
- Placement, in a fleet with a rule: a request that names a model (`options.model`) not in the set waits with the reason `model disabled: <id>`, checked first, before any trierarch. A request that names none fits only a trierarch whose reported default model for that harness (`options.properties.model.default`) is in the set; a harness with no default or no model option does not fit, and when no trierarch is left it waits with `model disabled: no enabled default model for <harness>`. The check before a request answers by the same rules, refused with the field `options` and the same reason.
- Only placing is checked. An assigned request, a restart after a crash and a ship its trierarch crews again keep their model; a request given back is placed under the rule. A change takes effect at the next assignment pass, and a request waiting on `model disabled` is placed once its model is enabled. The model a session states stays self-reported (0018): a session that switches to a disabled model is not stopped or told.
- Every signed-in session of the fleet reads the set, viewer included (`models.list`). Enabling and disabling a model takes `fleet:manage` (`models.enable`, `models.disable`); each answers the fleet's set, and enabling an enabled id or disabling one not in the set changes nothing.

Why: the fleet's operator answers for what its sessions cost and which vendors' models they use, and says so in one place. It is the operator's own rule, opt-in and empty by default (0016). Machines keep reporting what they can run; the rule filters on top of that and never edits a report. Core accepts a request naming any model (0029), so the trierarch plugin, which alone places, is the one guard. Exact ids, because what a harness reports and runs is an exact id.

Rejected: a deny list (a new model would be allowed by default, against the operator's choice); model families (aliases resolve to a different exact id with each harness release); a fleet setting in core (core never acts on crew settings, and only the trierarch plugin places); taking back assigned requests or stopping running sessions when a model is disabled (a final assignment is never moved, 0030).
